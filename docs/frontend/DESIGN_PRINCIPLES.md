# MuYun 前端设计原则

本文记录 MuYun 前端已经形成的设计哲学和稳定共识。它约束前端平台能力、业务页面、动态页面运行器和 UI adapter 的长期取舍。

## 核心定位

MuYun 前端不是单个业务后台，也不是 Ant Design Vue 的简单二次封装。它应逐步形成一组可被平台项目和业务项目共同消费的前端平台能力。

前端建设应以平台语义为中心。业务页面优先使用 MuYun 组件、MuYun client 和 MuYun runtime，不直接依赖底层 UI 库或裸 HTTP URL。静态业务页面和动态页面运行器应共享组件、字段、动作、错误、请求上下文和缓存语义。

## 螺旋迭代

MuYun 前端不采用先闭门建设完整组件库、再统一交付业务页面的方式，也不允许业务页面自由绕过平台能力形成事实标准。

组件和业务应螺旋迭代：

1. 先沉淀当前业务闭环必要的组件和 client。
2. 推进业务页面或动态页面运行器。
3. 从真实使用中发现组件、契约和非 UI 能力缺口。
4. 将稳定缺口上升到平台层，不稳定能力留在业务或示例中继续观察。

非 UI 能力和 UI 组件也应螺旋迭代。UI 组件可以随业务场景逐步加厚；HTTP、请求上下文、错误归一、权限、缓存、字典、引用和动作执行等非 UI 能力应尽早形成窄门面，避免业务项目重复封装。

## 业务闭环牵引

平台能力应由真实业务闭环牵引，而不是由抽象组件清单牵引。

每轮建设都应尽量围绕一个有代表性的页面、动作或动态运行链路展开，覆盖真实数据、真实动作、真实错误和真实刷新策略。这样沉淀出的契约更接近后端平台语义，也更容易被业务项目消费。

进入具体业务线前，应先固定平台主 UI 框架的承载形态。布局、菜单、菜单 tab、路由内容区、全局 loading、错误出口和上下文传递会影响后续所有页面，不应让业务页面各自形成实现。

## 能力上升

业务项目中的能力不自动进入平台层。能力上升应满足尽量多的条件：

1. 跨多个业务项目或多个模块复用。
2. 依赖平台标准语义，例如模块、字段、动作、字典、引用、附件、权限或审计。
3. 能通过稳定类型、props、事件、client 和文档交给下游团队使用。
4. 维护责任属于平台团队，或有明确共同维护机制。
5. 抽象后能明显降低业务项目代码量和风格分叉。

只服务单业务、语义未稳定或抽象收益不清楚的能力，应留在业务项目或示例中，不强行平台化。

## 垂直能力投入

垂直领域组件和能力可以在早期做深，但必须先判断场景是否足够清晰。

适合早期加深的能力通常具备：

1. 平台语义稳定。
2. 跨业务高频复用。
3. 后端能力边界清楚。
4. UI 形态变化空间有限。
5. 可通过类型、测试和示例稳定交付。

变化面大、业务面未看清或实现会明显扩张范围的能力，应控制投入并及时止损。

## 分层取舍

前端分层服务于长期演进，不服务于形式化拆目录。

| 层                     | 设计取舍                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| `web-contracts`        | 承载前后端共享的稳定语义、DTO、动作、字段、保存 envelope 和错误结构。                           |
| `web-core`             | 承载无 UI 的平台能力，例如 HTTP、请求上下文、错误、权限、Query 治理、字典、引用候选和动作执行。 |
| `vue-ui-antdv`         | 承载 Vue + Ant Design Vue adapter 和受控值归一，不承接平台数据获取和业务编排。                  |
| `platform-components`  | 承载跨业务复用、依赖平台标准能力、语义稳定的平台业务组件。                                      |
| `dynamic-page-runtime` | 将后端 descriptor、运行上下文、组件 registry 和平台 client 组合为动态页面能力。                 |
| `platform-workbench`   | 承载菜单、登录态、租户切换、全局错误出口和路由框架。                                            |

组件不应各自拼 URL、处理 token、解释权限、实现缓存失效或自定义错误展示。涉及这些能力时，应回到 `web-core`。

## 命名原则

包名表达 MuYun 归属，代码名表达职责。`@muyun/*` 保留品牌和发布边界；组件、类型、client 和函数不加 `Muyun` 前缀。基础 UI 组件使用 `Ui` 作为层级前缀并保持内外一致，例如 `UiForm`、`UiInput`、`UiSelect`、`UiTable`；平台语义组件直接使用职责名，例如 `ReferenceSelect`、`ActionBar`。`Dynamic`、`Platform`、`Admin` 等表达真实领域边界的前缀可以保留。

## Review 口径

前端 review 先看方向和边界，再看行为正确性，最后看组件细节。

重点判断：

1. 是否仍以平台语义和业务闭环为中心。
2. 是否避免业务页面绕过 MuYun client、MuYun 组件和 MuYun runtime。
3. 是否让静态业务页面和动态页面运行器共享字段、动作、错误、请求和组件语义。
4. 是否把稳定能力及时上升，把不稳定能力留在合适位置。
5. 是否为新增契约提供测试、边界检查或可运行示例。
