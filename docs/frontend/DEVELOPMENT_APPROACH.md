# MuYun 前端路线草案

本文记录 MuYun 前端后续推进步骤和路线目标。稳定设计哲学见 [MuYun 前端设计原则](DESIGN_PRINCIPLES.md)。

## 第一草案目标

第一阶段先定主 UI 框架和菜单承载闭环，再推进具体业务线。

优先顺序：

```text
必要非 UI 能力
必要基础 UI 组件
主 UI 框架
菜单渲染
菜单 tab 呼出
业务页面和动态运行态
```

这样先把企业后台平台的承载形态定住，避免后续页面各自处理布局、菜单、页签、路由状态、错误出口和上下文传递。

## 第一条闭环

第一条闭环聚焦主界面，而不是业务表单。

```text
启动应用
获取当前会话
获取菜单树
渲染 Shell 菜单
点击菜单
打开菜单 tab
内容区渲染占位页
```

这条链路应同时验证：

1. 会话、租户、菜单和路由语义是否能进入 `web-contracts`。
2. HTTP、请求上下文、错误、Query 治理、会话和菜单读取是否能进入 `web-core`。
3. 基础 UI adapter 是否能支撑菜单、页签、顶部栏、loading、empty 和 error。
4. `platform-shell` 是否能承载侧边菜单、顶部栏、内容区、菜单 tab 和全局状态出口。
5. 业务项目后续是否能通过 `@muyun/*` 包名复用同一套主框架。

## 第一阶段建议

第一阶段优先补齐主框架需要的窄门面，不追求完整业务运行态。

建议建设的非 UI 能力：

```text
HttpClient
RequestContext
AppError
createQueryClient
queryKeys
SessionContext
MenuClient
```

建议建设的 UI 能力：

```text
UiMenu
UiTabs
UiDropdown
UiSpin
UiEmpty
UiError
```

建议强化的 Shell 能力：

```text
AdminShell / PlatformShell
侧边菜单
顶部栏
用户和租户入口占位
内容区
菜单 tab 区
全局 loading / error outlet
路由出口
```

菜单数据可以先使用 mock client，但数据结构应贴近后端菜单剪枝后的消费结果。当前只做菜单消费和页面承载，不做菜单设计器、权限配置或复杂权限治理。

## 每轮推进步骤

一轮迭代应尽量包含：

1. 选定一个主框架能力链路。
2. 明确本轮需要复用的前后端平台语义。
3. 在 `web-contracts` 收口必要类型。
4. 在 `web-core` 补齐必要 client、上下文、错误和缓存入口。
5. 在 `vue-ui-antdv` 或 `platform-components` 沉淀必要 UI 能力。
6. 用 `platform-shell` 或业务示例完成可运行闭环。
7. 通过测试、边界检查或示例构建锁住新增契约。
8. 复盘哪些能力上升、保留、暂缓或明确不做。

## 能力归类清单

每轮结束后按以下口径归类：

| 归属 | 判断口径 |
| --- | --- |
| 当前要做 | 本轮主框架闭环必须依赖，且不做会导致后续页面绕过平台边界。 |
| 上升平台 | 语义稳定、跨业务复用、依赖平台标准能力，并能降低接入成本。 |
| 业务保留 | 只服务单业务，或抽象后收益不清楚。 |
| 后续预留 | 方向明确但当前闭环不需要，提前建设会扩大范围。 |
| 明确不做 | 业务面未看清、变化风险高，或与当前平台路线不一致。 |

## 第二阶段候选

主 UI 框架、菜单渲染和菜单 tab 呼出稳定后，再考虑动态业务运行态闭环。

候选链路：

```text
页面 bootstrap
列表查询
表单加载
字典和引用
保存 envelope
动作执行
错误展示和刷新
```

候选能力：

```text
字典 client
引用候选 client
动态记录保存 client
动作执行 client
字典选择
引用选择和回填
动作区
动态保存 envelope
查询表格基础形态
```

这些能力暂不作为第一阶段目标。只有当主框架承载形态稳定后，再进入正式设计和实现。

## 当前不宜重投入的方向

```text
完整低代码设计器
复杂可视化布局器
多 UI 库并行 adapter
超通用表格配置器
完整工作流可视化设计器
菜单设计器和权限配置器
```

这些能力变化面大，容易提前锁死错误抽象。只有当业务面和后端能力边界进一步清楚后，才进入正式设计。

## 验收口径

第一阶段完成时，应能说明：

1. 主 UI 框架是否能完成启动、会话、菜单、tab 和内容区闭环。
2. 哪些会话、菜单和路由语义进入了 `web-contracts`。
3. 哪些非 UI 能力进入了 `web-core`。
4. 哪些 UI 能力进入了 adapter 或平台组件。
5. 哪些能力被明确保留在业务侧、后续预留或暂不建设。
6. 用哪些测试、边界检查或示例构建证明契约有效。
